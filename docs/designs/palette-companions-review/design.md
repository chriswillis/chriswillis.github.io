# Architecture and Economics-Brainstormer — raw report

No architectural blocker to a static, client-side implementation. The main costs are browser computation, state complexity, and persistence size; no backend or LLM service is needed.

- **Major — State integrity and cache cost.** The page currently has one generated result, a shallow copy of the reference palette list, and models cached by palette ID. Adding edited ramps directly to that structure risks changing the reference or retaining a stale model. Recommend separate immutable reference data, generated baselines, proposed suggestions, accepted edits, selection, and active-column state. Resolve what happens to accepted edits when the brand, palette, or generation mode changes, and whether reset restores the authored ramp or its accepted suggestion.
- **Major — Suggestion algorithm boundaries.** Existing `seedMap` provides relative colorfulness (`sRaw`), but it is measured at the seed’s particular hue and lightness; near-neutral seeds have no useful hue and may substitute a neutral ramp. Copying this factor indiscriminately across companions could flatten a palette or push many steps into gamut compression. Recommend a deterministic, bounded transformation with an explicit near-neutral fallback, preserving each source ramp’s lightness sequence and reporting compression. Still unresolved: whether colorfulness comes from the first brand seed, both seeds, or the generated brand ramp, and whether hue identities refer to all authored ramps or only lofted ramps.
- **Major — Local computation budget.** Input changes currently synchronously regenerate and redraw every panel. Imports permit 200,000 characters but have no explicit ramp/step count limit. The engine’s longest decreasing subsequence is quadratic in steps; categorical checks across every selected swatch would add quadratic pair comparisons, multiplied by simulation modes. Recommend limits on parsed ramps, steps, and suggestion candidates, caching against immutable inputs, and computing only the metrics used by the chosen preview. Establish latency targets through measurement before requiring a worker. Built-in palettes are modest—at most 25 chromatic ramps and 16 steps—but the import limit alone does not bound computation adequately.
- **Major — Export and persistence semantics.** Existing exports serialize one ramp; URL state contains generation controls and a palette ID, while imported references live only in browser storage. Adding multiple editable columns requires stable IDs and collision-safe export names. Recommend one shared scope resolver for preview/copy/download, explicit definitions of active/selected/full, versioned saved state, and visible recovery from storage failure. Decide whether “full” includes unused authored columns, excluded interior ramps, all neutrals, and poles. Decide whether shared links must reproduce imported references and accepted edits; otherwise retain the current clearly explained browser-local limitation. Avoid placing unbounded snapshots in the URL.
- **Major — Metrics must describe actual displayed colors.** Wide-gamut internal colors, clipped hex fallbacks, and simulated colors can differ. Existing `Engine.Y` and contrast output do not provide a complete categorical evaluation pipeline. Recommend recording gamut/fallback, background, representative chart step, and simulation mode with each result. Contrast and categorical distance must remain separate, as already accepted. Resolve the preview’s color-selection rule before choosing pairwise metrics; comparing every tint against every tint is expensive and often irrelevant.
- **Nit — Complete reference inventory.** `renderFamily` currently uses `M.loft`, which excludes authored ramps that cross in hue. A builder promising selection of existing columns and preservation of the full reference should source its inventory from reference data, while retaining loft membership solely as a generator concern. Neutral scales can also have different step names and lengths, so columns should retain their own step keys.

The existing tests cover useful invariants—invalid drafts, precise input restoration, transactional import storage, and step-pin behavior—but not multi-column transitions. Preserve these and add targeted state-transition coverage when the interaction contract is settled.
